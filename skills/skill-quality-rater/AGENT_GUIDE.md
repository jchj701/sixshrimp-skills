# Skill Quality Rater — AI Agent 操作指南

> **版本**：v1.0
> **目的**：让 AI Agent 独立完成 Skill 质量评估，无需人工干预
> **前置条件**：已安装 Python 3.7+，可执行 Shell 命令

---

## 1. 概述

### 1.1 这是什么

Skill Quality Rater 是一个系统化的 Skill 质量评估工具，通过 8 个维度对 Skill 进行量化评分，帮助识别问题、给出改进建议。

### 1.2 能做什么

- **完整评估**：对 Skill 进行 8 维度全面评估
- **快速评估**：只评估最关键的 3 个核心维度（适合时间敏感场景）
- **批量评估**：对多个 Skill 进行横向对比

### 1.3 输出什么

- 量化评分（0-10 分，精度 0.1 分）
- 等级评定（S/A/B/C/D 级）
- 8 维度详细分析
- 具体改进建议
- 完整的 Markdown 格式评估报告

## 3. 理解评分体系

### 3.1 8 维度定义与权重

| 维度 | 名称 | 权重 | 核心检查点 |
|:---:|:---|:---:|:---|
| **D1** | 触发精准度 | 15% | description 含"when to use"、触发词无冲突、无层错位 |
| **D2** | 分层合理性 | 20% | 触发条件在 frontmatter、参考细节在 references、scripts 执行不读入 |
| **D3** | 自由度匹配 | 20% | 脆弱操作→脚本、创造性→文字、判断"该用哪种" |
| **D4** | 简洁约束 | 15% | 无 README/CHANGELOG、每句话值得 token、无冗余 |
| **D5** | 反模式表达 | 10% | "不做什么"比"做什么"精确、有反转测试 |
| **D6** | 资源组织 | 10% | scripts/references/assets 区分正确、无重复 |
| **D7** | 领域适配 | 5% | 是否符合领域最佳实践 |
| **D8** | 安全边界 | 5% | 无危险命令、无敏感信息泄露 |

### 3.2 评分等级映射

| 等级 | 分数范围 | 说明 |
|:---:|:---:|:---|
| **S** | 9.0 - 10.0 | 优秀，可直接作为范本 |
| **A** | 8.0 - 8.9 | 良好，小改进即可 |
| **B** | 7.0 - 7.9 | 及格，有明显短板 |
| **C** | 6.0 - 6.9 | 不及格，需重写 |
| **D** | < 6.0 | 失败，建议删除重来 |

### 3.3 各维度精确评分标准

#### D1. 触发精准度（权重 15%）

| 得分 | 表现 |
|:---:|:---|
| 9-10 | description 完整含 when to use，触发词无冲突 |
| 7-8 | 基本完整，缺少个别要素 |
| 5-6 | 缺少 when to use |
| 3-4 | 触发条件在 body（而非 frontmatter） |
| <3 | 严重缺失 |

**典型扣分**：
- description 只说"做什么"不说"什么时候用" → -2分
- 触发条件写在 body 而非 frontmatter → -3分

#### D2. 分层合理性（权重 20%）

| 得分 | 表现 |
|:---:|:---|
| 9-10 | L1/L2/L3 完美分层 |
| 7-8 | 基本正确，有小问题 |
| 5-6 | 有层错位（参考细节塞进 SKILL.md） |
| <5 | 完全混乱 |

**典型扣分**：
- 参考细节塞进 SKILL.md → -2分
- 确定性操作写成文字（应该用脚本） → -3分

#### D3. 自由度匹配（权重 20%）

| 得分 | 表现 |
|:---:|:---|
| 9-10 | 脆弱操作全部脚本化，创造性任务保持自由度 |
| 7-8 | 基本匹配，个别可以优化 |
| 5-6 | 有缺失或过度约束 |
| 3-4 | 脆弱操作没脚本，或创造性任务被过度约束 |
| 0-2 | 完全没考虑自由度问题 |

**典型扣分**：
- 脆弱操作（文件IO）没脚本 → -3分
- 创造性任务过度约束 → -2分
- 确定性操作写成冗长文字 → -2分

#### D4. 简洁约束（权重 15%）

| 得分 | 表现 |
|:---:|:---|
| 9-10 | 无冗余 |
| 7-8 | 基本简洁 |
| 5-6 | 有冗余内容 |
| <5 | 大量冗余 |

**禁止文件及扣分**：
- README.md → -2分
- CHANGELOG.md → -2分
- TODO.md → -1分
- CONTRIBUTING.md → -1分
- LICENSE → -1分
- HISTORY.md → -1分
- SUPPORT.md → -1分

#### D5. 反模式表达（权重 10%）

| 得分 | 表现 |
|:---:|:---|
| 9-10 | 反模式清晰完整，正反对比明确 |
| 7-8 | 有但不全面 |
| 5-6 | 只有正面描述，无反模式 |
| <5 | 完全无反模式 |

**典型扣分**：
- 只有正面描述无反模式 → -2分

#### D6. 资源组织（权重 10%）

| 得分 | 表现 |
|:---:|:---|
| 9-10 | scripts/references/assets 完全分离 |
| 7-8 | 基本正确 |
| 5-6 | 有混淆或重复 |
| <5 | 完全混乱 |

**检查要点**：
- scripts/ 是否只包含可执行脚本（.py/.sh/.js）？
- references/ 是否只包含参考资料（.md/.yaml）？
- 有无内容重复？

#### D7. 领域适配（权重 5%）

| 得分 | 表现 |
|:---:|:---|
| 9-10 | 完全符合领域最佳实践 |
| 7-8 | 基本符合 |
| <7 | 有偏差 |

**领域规则库**（见 domain_rules/）：
- `document-processing.md`：文档处理领域
- `data-analysis.md`：数据分析领域
- `code-development.md`：代码开发领域

#### D8. 安全边界（权重 5%）

| 得分 | 表现 |
|:---:|:---|
| 9-10 | 无安全问题 |
| 7-8 | 基本安全 |
| <7 | 有安全隐患 |

**检查要点**：
- 是否有危险命令（如 `rm -rf`）？
- 是否有敏感信息泄露？
- 是否执行用户输入的原始命令？

### 3.4 自由度光谱概念

**核心思想**：任务处于"确定性"到"创造性"的光谱上，需要不同的约束方式。

```
低自由度 ════════════════════════════ 高自由度
    │                                    │
    ▼                                    ▼
确定性操作                          创造性任务
（必须精确执行）                    （允许自由发挥）
```

#### 两条黄金法则

1. **脆弱操作 → 用脚本锁定**
   - 原因：文字描述无法覆盖所有边界情况
   - 示例：文件IO、API调用、格式转换

2. **创造性任务 → 用原则约束**
   - 原因：过度约束会限制 AI 的能力
   - 示例：写文案、做设计、方案设计

#### 必须用脚本的操作（低自由度）

| 操作类型 | 原因 | 示例 |
|:---|:---|:---|
| 文件读取 | 路径可能不存在、权限可能不足 | `read_file(path)` |
| 文件写入 | 可能目录不存在、磁盘可能满 | `write_file(path, content)` |
| 文件删除 | 不可逆操作，必须精确 | `rm(path)` |
| 目录创建 | 父目录可能不存在 | `mkdir(path)` |
| API调用 | 网络可能超时、可能返回错误 | `fetch_api(url)` |
| 格式转换 | 规则复杂，容易出错 | JSON→CSV、Markdown→HTML |
| 参数解析 | 边界情况多 | 命令行参数处理 |
| 编码处理 | 字符集问题 | UTF-8/GBK 转换 |

#### 建议用文字的操作（高自由度）

| 操作类型 | 原因 | 示例 |
|:---|:---|:---|
| 文案生成 | 需要创意和灵活性 | 产品介绍、营销文案 |
| 方案设计 | 需要根据情况调整 | 解决方案、技术架构 |
| 代码编写 | 需要理解上下文 | 实现某个功能 |
| 风格把控 | 需要灵活处理 | 语气、表达方式 |
| 问题分析 | 需要推理和判断 | 原因分析、诊断 |

### 3.5 反模式概念

**反模式**：告诉 AI"不做什么"的说明，与正面指导同等重要。

**反转测试**：每条正面指导能否改写为"不要做 X"？

**示例**：
- 正面："保持专业语气"
- 反面："不要使用口语化表达，如'搞定'、'没问题'等"

**常见反模式问题**：
- 只有正面描述，无"不做什么"
- 反模式比正面描述更模糊
- 缺少边界情况说明

### 3.6 禁止文件列表

以下文件**不应出现**在 Skill 目录中：

| 文件名 | 原因 |
|:---|:---|
| README.md | Skill 说明在 SKILL.md 中 |
| CHANGELOG.md | 开发记录，不应出现 |
| TODO.md | 临时文件，应清理 |
| CONTRIBUTING.md | 开发指南，不应出现 |
| LICENSE | 许可证，不应出现 |
| HISTORY.md | 历史记录，不应出现 |
| SUPPORT.md | 支持信息，不应出现 |

### 3.7 分层架构（L1/L2/L3）

Skill 内容分为三个层级：

```
┌─────────────────────────────────────────────────────────┐
│  L1 层：原则指导（WHY）                                   │
│  位置：SKILL.md 顶部                                      │
│  内容：告诉 AI "为什么这样做"                             │
├─────────────────────────────────────────────────────────┤
│  L2 层：操作指引（HOW）                                    │
│  位置：SKILL.md 正文                                      │
│  内容：告诉 AI "具体怎么做"                               │
├─────────────────────────────────────────────────────────┤
│  L3 层：参考细节（WHAT）                                   │
│  位置：references/ 目录                                   │
│  内容：告诉 AI "具体参数/格式是什么"                      │
│  特点：零 token 成本（按需读取）                           │
└─────────────────────────────────────────────────────────┘
```

**各层职责**：

| 层级 | 位置 | 内容 | Token 成本 |
|:---:|:---|:---|:---:|
| L1 原则 | SKILL.md 顶部 | 决策指导(WHY) | 必读 |
| L2 操作 | SKILL.md 正文 | 步骤流程(HOW) | 必读 |
| L3 参考 | references/ | 详细规格(WHAT) | 按需 |

**常见层错位问题**：
- ❌ L3 参考细节塞进 SKILL.md（如 API 参数列表、完整模板）
- ❌ L1/L2 塞进 references/
- ❌ scripts 当资料读（如"读取 scripts/template.py 的内容"）

## 5. 执行评估（核心步骤）

### 5.1 读取目标 Skill 全部文件

#### 必读文件

1. **SKILL.md**（主文件）
   - frontmatter（YAML 头部）
   - description（描述）
   - body（正文）

2. **references/** 目录（所有文件）
   - 逐个读取，理解参考内容

3. **scripts/** 目录（所有文件）
   - 检查脚本实现
   - 注意：scripts 不应被当作文本读入

4. **其他配置文件**
   - .yaml、.json 等

#### 检查清单

```
□ SKILL.md 是否存在？
□ frontmatter 是否包含 name、description？
□ description 是否包含"when to use"？
□ references/ 目录是否存在？包含哪些文件？
□ scripts/ 目录是否存在？包含哪些脚本？
□ 是否有禁止文件（README.md、CHANGELOG.md 等）？
```

### 5.2 按 8 维度逐一评估

对每个维度进行评估，记录：
- **得分**（0-10，精度 0.1）
- **证据**（原文引用）
- **问题**（如有问题）

#### 维度评估详细指南

---

**D1. 触发精准度**

| 检查点 | 操作 |
|:---|:---|

| 触发条件是否在 frontmatter？ | 检查 YAML 头部 |
| 触发词是否与其他 Skill 冲突？ | 使用 trigger_collision.py |

1. description 有"when to use"？→ +2分

### 5.3 计算加权总分

```
总分 = Σ(维度得分 × 权重)

D1权重: 15% = 0.15
D2权重: 20% = 0.20
D3权重: 20% = 0.20
D4权重: 15% = 0.15
D5权重: 10% = 0.10
D6权重: 10% = 0.10
D7权重: 5%  = 0.05
D8权重: 5%  = 0.05

示例计算：
D1: 8.0 × 0.15 = 1.20
D2: 7.5 × 0.20 = 1.50
D3: 8.5 × 0.20 = 1.70
```

## 7. 注意事项

### 7.1 交叉验证

- 每个维度的评分必须有**原文证据**支撑
- 避免主观臆断，基于文件内容进行判断
- 如有疑问，参考 dimension_rubric.md 的详细标准

### 7.2 可溯源

- 所有扣分项必须标注**原文位置**（文件、行号）
- 报告必须包含被评估 Skill 的 Git Revision
- 确保评估结果可复现

### 7.3 公正性

- 严格按照评分标准打分，不因整体印象调整
- 区分"建议优化"和"必须修复"
- 对不同领域保持一致的评价标准

### 7.4 证据链要求

每个扣分项必须包含：
1. **维度**：哪个维度（D1-D8）
2. **问题**：具体是什么问题
3. **证据**：原文引用
4. **影响**：对 Skill 质量的影响程度
5. **建议**：如何修复

### 7.5 快速评估模式

如时间有限，可只评估 3 个核心维度：

| 维度 | 名称 | 权重 |
|:---:|:---|:---:|
| D1 | 触发精准度 | 30% |
| D2 | 分层合理性 | 35% |
| D3 | 自由度匹配 | 35% |

**注意**：快速评估只给出初步判断，不作为最终评分。
